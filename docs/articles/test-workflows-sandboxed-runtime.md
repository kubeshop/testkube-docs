# Running Test Workflows in a sandboxed container runtime

Test Workflows can run code you have not written or reviewed: third-party tools, community images, or tests generated by an AI agent. In a standard container, that code shares the node's kernel with every other pod on the node, so a kernel vulnerability exploited from a test can reach the node and the workloads beside it. A sandboxed container runtime such as [gVisor](https://gvisor.dev/) gives each pod its own kernel layer, so test code cannot reach the node kernel directly.

To run Test Workflows in a sandboxed runtime, send the runner's executions to a dedicated namespace and let cluster admission policies assign the runtime to every pod created there. Testkube runs each workflow as standard Kubernetes pods, so the policies cover every pod a workflow creates, with no changes to the workflows themselves. This page builds the setup with gVisor and Kyverno, in three steps:

1. Admission policies on a dedicated sandbox namespace give every pod created there the gVisor runtime class, and reject any pod without it.
2. The runner runs executions in the sandbox namespace by default.
3. A dry run and a verification workflow confirm that pods start under gVisor.

Other runtimes that Kubernetes selects through a RuntimeClass, such as Kata Containers, follow the same pattern with their own runtime class name, node setup and verification check.

## Where Testkube meets the sandbox

The setup spans five systems: the Testkube runner, an admission policy engine, Kubernetes, the container runtime and network policy. Each row in the following table is a point where Testkube's behavior decides what one of the other systems must do. The steps implement every row with Kyverno and gVisor; with other tools, the last two columns are what to agree with whoever owns each system.

| Interface point          | What Testkube does                                                                                                                                                                                       | What the sandbox setup must do                                                                                                                           | Owned by                |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| Jobs and pods            | The runner creates a Job for each execution, and the Job creates the pod. Services and parallel workers are further pods, created from inside the execution.                                             | The policies act on pods, not on Jobs, and on every pod created in the namespace.                                                                        | Admission policy engine |
| Node placement           | The Kubernetes scheduler places execution pods like any other pods, using the node selectors and tolerations the workflow sets.                                                                          | If only some nodes run gVisor, sandbox pods get a node selector and toleration for those nodes.                                                          | Admission policy engine |
| Pod settings             | A workflow can set pod-level fields, including volumes.                                                                                                                                                  | gVisor passes `hostPath` volumes through to the node's real files, so the namespace rejects them. The Pod Security Standards `baseline` level does this. | Kubernetes              |
| Execution ServiceAccount | Execution pods use a ServiceAccount that can create, change and delete pods, jobs, secrets, configmaps and persistent volume claims in the namespace. Testkube needs it for services and parallel steps. | Code in the sandbox can start new pods, so the namespace must stop those pods from requesting host access. The same `baseline` level does this.          | Kubernetes              |
| Execution namespace      | The runner creates execution pods in `execution.default.namespace`, or in a namespace a workflow names if it is listed under `execution.additionalNamespaces`. It rejects any other namespace.           | Every namespace the runner allows carries the same admission policies and Pod Security label.                                                            | Testkube runner         |
| Containers in each pod   | Every execution pod includes Testkube's setup and toolkit containers alongside your test containers.                                                                                                     | The runtime applies to all of them. Testkube's containers run under gVisor with shell steps, services and parallel workers.                              | Container runtime       |
| Network                  | Executions connect to the applications under test and to the Testkube components described in [Testkube Architecture](/articles/architecture).                                                           | gVisor does not restrict the network. Any egress policy keeps those connections open.                                                                    | Network policy          |

## Prerequisites

- A Kubernetes cluster with a RuntimeClass for gVisor, using the handler `runsc`. The samples assume the RuntimeClass is named `gvisor`.
- If only some nodes run gVisor, a label and a `NoSchedule` taint on those nodes, so that sandbox pods can be steered onto them.
- Kyverno 1.19 or later, which provides the `policies.kyverno.io/v1` MutatingPolicy and ValidatingPolicy types.
- A Testkube runner installed from the `testkube-runner` Helm chart, version 2.14.2 or later. See [Installing Testkube Runner with Helm Charts](/articles/multi-agent-runner-helm-chart).

## Create the sandbox namespace and admission policies

The following sample creates the sandbox namespace and two Kyverno policies. Together they cover the Jobs and pods, node placement, pod settings and execution ServiceAccount rows of [Where Testkube meets the sandbox](#where-testkube-meets-the-sandbox):

- The Namespace carries the Pod Security Standards `baseline` label.
- The MutatingPolicy matches pods created in `testkube-sandbox`, selected by the namespace's `kubernetes.io/metadata.name` label. Its first patch sets `runtimeClassName`; the second and third add the node selector and toleration, either into the pod's existing values or as new fields when the pod has none.
- The ValidatingPolicy matches the same pods, and its single expression denies any pod whose `runtimeClassName` is not `gvisor`, so a pod the mutation misses is rejected instead of starting on the node kernel.

Replace the example label and taint `sandbox.example.com/runtime=gvisor` with the ones on your gVisor nodes. If every node runs gVisor, keep only the first patch, the one that sets `runtimeClassName`. If only some nodes run gVisor, keep all three: without the placement patches, a sandbox pod can land on a node without gVisor and never start, while the execution stays in the running state (see [Troubleshooting](#an-execution-stays-in-running-without-progress)).

```yaml title="testkube-sandbox-policies.yaml"
apiVersion: v1
kind: Namespace
metadata:
  name: testkube-sandbox
  labels:
    pod-security.kubernetes.io/enforce: baseline
---
apiVersion: policies.kyverno.io/v1
kind: MutatingPolicy
metadata:
  name: testkube-sandbox-gvisor-mutate
spec:
  failurePolicy: Fail
  autogen:
    podControllers:
      controllers: []
  matchConstraints:
    namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: testkube-sandbox
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE"]
        resources: ["pods"]
  mutations:
    - patchType: JSONPatch
      jsonPatch:
        expression: >
          [
            JSONPatch{op: "add", path: "/spec/runtimeClassName", value: "gvisor"},
            has(object.spec.nodeSelector)
              ? JSONPatch{op: "add",
                  path: "/spec/nodeSelector/" + jsonpatch.escapeKey("sandbox.example.com/runtime"),
                  value: "gvisor"}
              : JSONPatch{op: "add", path: "/spec/nodeSelector",
                  value: {"sandbox.example.com/runtime": "gvisor"}},
            has(object.spec.tolerations)
              ? JSONPatch{op: "add", path: "/spec/tolerations/-",
                  value: Object.spec.tolerations{key: "sandbox.example.com/runtime",
                    operator: "Equal", value: "gvisor", effect: "NoSchedule"}}
              : JSONPatch{op: "add", path: "/spec/tolerations",
                  value: [Object.spec.tolerations{key: "sandbox.example.com/runtime",
                    operator: "Equal", value: "gvisor", effect: "NoSchedule"}]}
          ]
---
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: testkube-sandbox-gvisor-validate
spec:
  failurePolicy: Fail
  validationActions: [Deny]
  autogen:
    podControllers:
      controllers: []
  matchConstraints:
    namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: testkube-sandbox
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE"]
        resources: ["pods"]
  validations:
    - expression: "has(object.spec.runtimeClassName) && object.spec.runtimeClassName == 'gvisor'"
      message: "Pods in testkube-sandbox must run under the gvisor runtime class."
```

Apply the file:

```sh
kubectl apply -f testkube-sandbox-policies.yaml
```

### Settings in the sample that are required

Three settings in this sample are required:

- **`patchType: JSONPatch`.** `nodeSelector` and `tolerations` can only be added to with JSONPatch; with ApplyConfiguration, Kyverno rejects every pod in the sandbox namespace. JSONPatch also keeps any node selector and tolerations the pod already has.
- **Autogen off on both policies** (`autogen.podControllers.controllers: []`). Without it, Kyverno also applies the policies to the Jobs Testkube creates, and the ValidatingPolicy rejects them before any pod exists.
- **`failurePolicy: Fail`.** If Kyverno is unavailable, pods in the sandbox namespace are rejected rather than started without gVisor.

## Configure the runner

The runner's `execution.default.namespace` setting moves executions into a namespace separate from the runner, as described in [Install runner in one namespace and run executions in another](/articles/multi-agent-runner-helm-chart#install-runner-agent-in-one-namespace-and-run-executions-in-another). Set it to the sandbox namespace in your runner's `values.yaml`:

```yaml title="values.yaml"
execution:
  default:
    namespace: testkube-sandbox
```

Create the sandbox namespace before you change the runner. The chart creates the execution ServiceAccount, Role and RoleBinding in that namespace, but not the namespace itself.

To change an installed runner without editing its values file, run `helm upgrade` with `--reuse-values`, which keeps the existing values and changes only `execution.default.namespace`. Use your runner's release name and namespace, and the chart version the runner already runs, which `helm list -n my-runner` shows. Combining `--reuse-values` with a newer chart version can fail when the newer chart adds values.

```sh
helm upgrade \
  --namespace my-runner \
  --reuse-values \
  --set 'execution.default.namespace=testkube-sandbox' \
  my-runner oci://us-east1-docker.pkg.dev/testkube-cloud-372110/testkube/testkube-runner --version <installed-version>
```

A workflow that sets no `job.namespace` now runs in the sandbox namespace, under gVisor.

The runner only runs executions in its default namespace and the namespaces listed under [`execution.additionalNamespaces`](/articles/multi-agent-runner-helm-chart#support-additional-namespaces). A workflow that sets `job.namespace` to any other namespace, including the runner's own, is rejected with `namespace <name> not supported`.

Do not also list the sandbox namespace under `execution.additionalNamespaces`; it is already covered as the default.

## Verify the sandbox

To check the policies before you run a workflow, run a server-side dry run of a plain pod. Kubernetes passes the pod through admission without creating it, so the output is the runtime class the MutatingPolicy assigned. Expect `gvisor`. A denial from `testkube-sandbox-gvisor-validate` means the ValidatingPolicy is enforcing but the MutatingPolicy is not applying.

```sh
kubectl run probe --image=alpine -n testkube-sandbox --dry-run=server -o jsonpath='{.spec.runtimeClassName}'
```

To check the runtime from inside the containers, run the following workflow. It sets no `job.namespace`, so it reaches the sandbox namespace only through the runner configuration. The workflow also starts a service and two parallel workers, so it covers every type of pod a Test Workflow creates.

```yaml title="sandbox-check.yaml"
apiVersion: testworkflows.testkube.io/v1
kind: TestWorkflow
metadata:
  name: sandbox-check
spec:
  container:
    image: alpine:3.20
  services:
    web:
      image: nginx:1.27-alpine
      readinessProbe:
        httpGet:
          path: /
          port: 80
  steps:
    - name: Main pod runtime
      shell: |
        echo "kernel: $(uname -r)"
        dmesg | grep -qi gvisor && echo "RESULT: under gVisor" || (echo "RESULT: NOT gVisor" && exit 1)
    - name: Reach the sandboxed service
      shell: wget -qO- http://{{ services.web.0.ip }} | grep -i nginx
    - name: Parallel workers
      parallel:
        count: 2
        container:
          image: alpine:3.20
        shell: |
          echo "worker {{ index }} kernel: $(uname -r)"
          dmesg | grep -qi gvisor && echo "RESULT: worker under gVisor" || (echo "RESULT: NOT gVisor" && exit 1)
```

A passing run shows the following:

- **Main pod and each worker:** the kernel version from `uname -r`, which under gVisor differs from the node's, followed by `RESULT: under gVisor` or `RESULT: worker under gVisor`. The `dmesg` check decides the result; without gVisor, the step prints `RESULT: NOT gVisor` and fails.
- **Service step:** the title of the Nginx page. The step fails if the page does not arrive.

To see the same result from the cluster side while the workflow runs, list the pods in the sandbox namespace. The `RUNTIME` column shows `gvisor` for every pod, and if only some nodes run gVisor, the `NODE` column shows only those nodes.

```sh
kubectl get pods -n testkube-sandbox -o custom-columns=NAME:.metadata.name,RUNTIME:.spec.runtimeClassName,NODE:.spec.nodeName
```

## Running with the sandbox

- **No per-workflow changes.** Every workflow this runner executes that sets no `job.namespace` runs in the sandbox, including workflows created later.
- **The sandbox is per runner.** Workflows that run on any other runner in the environment run without the sandbox, unless that runner is configured the same way. To sandbox only some workflows, give them a dedicated runner and target it, as described in [Runner Targeting](/articles/test-workflows-running#runner-agent-targeting).
- **New images.** Before you rely on the sandbox for a new image, run `sandbox-check` with that image.
- **New gVisor nodes.** When you add gVisor nodes, give them the same label and taint, so sandbox pods can be placed on them.
- **Where the setup stops.** The sandbox covers execution pods in the sandbox namespace on this runner. [Considerations](#considerations) lists what it leaves to the other systems.

## Considerations

The setup covers the rows in [Where Testkube meets the sandbox](#where-testkube-meets-the-sandbox). It leaves the following points to the system named in brackets, so raise each one with whoever owns that system.

- **Availability (admission policy engine).** With `failurePolicy: Fail`, no sandboxed execution can start while Kyverno is unavailable. Run Kyverno with enough replicas that an outage of one pod does not stop executions.
- **Stricter pod security (Kubernetes).** The `restricted` Pod Security level also requires non-root containers, which many test images do not support. Move to it only if your test images run as non-root, and run `sandbox-check` after the change.
- **Kubernetes API access (Kubernetes).** The execution ServiceAccount can still create and read objects in the sandbox namespace, including secrets. [Disable access to Kubernetes from executions](/articles/multi-agent-runner-helm-chart#disable-access-to-kubernetes-from-executions) removes that access, but it also disables services and parallel steps, so `sandbox-check` fails. Use it for runners whose workflows use neither.
- **Additional namespaces (Testkube runner).** If the runner also lists namespaces under `execution.additionalNamespaces`, a workflow can run in one of those instead, without gVisor unless that namespace carries the same admission policies. Give every listed namespace the same admission policies and Pod Security label, or leave the list empty.
- **The runner pod (Testkube runner).** The runner stays in its own namespace and is not sandboxed; only execution pods are. Test code runs in execution pods, not in the runner pod, so no action is needed unless your policy requires every pod in the cluster to run sandboxed.
- **Compatibility (container runtime).** gVisor does not implement every Linux system call, so some images, such as those that run a browser, may not run. Images that need privileged mode, such as Docker-in-Docker, are rejected by the `baseline` label. Check each image with `sandbox-check` before you rely on it.
- **Performance (container runtime).** gVisor adds overhead to system calls and I/O. Expect slower runs for tests that make many system calls or read and write heavily, and set execution timeouts with that in mind.
- **Network egress (network policy).** gVisor does not restrict outbound traffic. A NetworkPolicy can block destinations tests do not need, for example the cloud metadata endpoint `169.254.169.254`, which on cloud-hosted nodes can return the node's cloud credentials. Keep the connections listed in the network row open, run `sandbox-check` afterwards, and check that the cluster's network plugin enforces NetworkPolicies.

:::warning

The runner's [Global Template](/articles/multi-agent-runner-helm-chart#setting-global-template) can also set `job.namespace` for workflows that set none. It sets only a default: a workflow's own `job.namespace` overrides it, and that workflow's pods run outside the sandbox namespace without gVisor. Do not use the Global Template to isolate executions.

:::

## Troubleshooting

### An execution stays in running without progress

The pod was most likely placed on a node without gVisor, so it never starts. Look for the event `no runtime for "runsc" is configured` in the sandbox namespace:

```sh
kubectl get events -n testkube-sandbox
```

If the event is there, check that your gVisor nodes carry the label and taint, and that the MutatingPolicy's placement patches use the same label and taint.

### Every pod in the sandbox namespace is rejected with `may not mutate atomic arrays, maps or structs`

The MutatingPolicy uses `ApplyConfiguration`. Switch it to `patchType: JSONPatch`, as in the sample.

### The execution fails before any pod starts, with a Job rejected by `testkube-sandbox-gvisor-validate`

Autogen is on. Set `autogen.podControllers.controllers: []` on both policies.

### Pods are rejected although the policies look correct

Check that Kyverno is running. With `failurePolicy: Fail`, Kubernetes rejects pods in the sandbox namespace while Kyverno is unavailable. If Kyverno is running, read the rejection message: a pod that requests a setting the `baseline` label forbids, such as a `hostPath` volume, is rejected by Pod Security, and the message names the setting.

### A step fails only under gVisor

The image may use a system call that gVisor does not implement. To confirm, run the same workflow on a runner without the sandbox.
